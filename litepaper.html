1. Abstract

Boats n Hoes is an open-source experiment in putting overlooked consumer GPUs to useful work. A central coordinator hands out small, signed AI jobs; workers running on volunteers' graphics cards do them and send results back; and the coordinator checks the work with hidden re-runs and known-answer tests before it counts. Counted work is tallied as simulated, off-chain points in reports that are signed and can be re-checked by anyone.

The hard problem isn't running a model. It's knowing a result is real when the person running it might cheat, without paying to redo every job. This paper describes how the prototype approaches that, what it can and can't prove, and how a coin is proposed to fit in later. The first milestone is deliberately modest: prove the software on two Radeon RX 470 cards in public, before any chain or token exists.

3. Why useful work

Classic proof-of-work mining turns electricity into security by having machines solve puzzles nobody needs answered. That has real strengths: coins are spread to whoever does the work, and attacking the chain costs real hardware. But the work itself is thrown away, and the cost of mining doesn't make a coin valuable; only demand does.

The bet here is different: GPUs doing work someone actually wants (answering prompts, classifying or extracting text) is useful whether or not a coin ever exists. The catch is that useful work is much harder to check than a hash. A hash puzzle can be verified in microseconds; an AI answer can only be checked by running the job again or comparing it against a known answer. Most of this paper is about doing that cheaply and without being fooled.

There is no inexpensive cryptographic proof that a particular model ran correctly on a particular GPU. The prototype doesn't pretend otherwise: it relies on sampling, hidden tests and agreement between independent rigs, and says how much each is worth.

4. System overview

          Operator (owner)
               |
         Coordinator  ── signs jobs (Ed25519), keeps the ledger (SQLite)
          /        \
   Rig A worker   Rig B worker   ── one worker per GPU, own key each
     RX 470 4 GB    RX 470 8 GB
          \        /
       results + receipts
               |
   Checks: re-runs · hidden tests · tie-breakers · review queue
               |
   Simulated points ── signed reports ── public logbook

The coordinator is a small web service (FastAPI) with one SQLite ledger. It is trusted: it is run by the project, not a decentralised network. The design tries to make that trust checkable after the fact (signed reports, shareable ledger copies) rather than pretending it isn't there.

5. Jobs and receipts

Job manifest (bnh-job/1)

Each job names its task type, its input (with a sha256 of it), its points, a deadline, and for model tasks the sha256 of the exact model file. The coordinator signs the whole manifest with an Ed25519 key; workers pin the coordinator's public key and refuse anything unsigned, altered or of an unknown version. Two task types exist today:

  • demo:sha256: a trivial hashing task used to test the plumbing.
  • llm:generate: run a pinned open model (first candidate: Qwen2.5 0.5B Instruct, Q4_K_M, about 400 MB, Apache-2.0) on a prompt with a fixed seed and token limit, through llama.cpp's Vulkan backend.

Receipt (bnh-receipt/1)

A worker's answer comes with a receipt repeating the job version, the hash of the input it ran and the model file it checked. The coordinator refuses receipts that don't match. This catches honest mistakes (a stale model file, an old worker), but it is not proof: a cheater can copy the expected values without running anything. Only the checks in section 7 catch that.

Model files

Models are never downloaded automatically. The operator downloads one, and it's pinned by size and sha256 (checked against the hash on the model's page) before any job can use it. Downloads are https-only with size and time limits, and every model's licence is recorded.

Leases

A rig that takes a job holds it for a lease long enough for that job's own time limit plus time to re-check the model file, so an honest, slow AI job isn't taken away mid-run. A job whose deadline is shorter than its own run limit is refused when queued.

6. Rigs and identity

  • Enrollment: the operator issues a one-time code per rig, tied to an owner label. The rig exchanges it for its own key; the coordinator stores only a hash of the key. Rigs can be revoked instantly.
  • Same owner, no self-checks: a rig never checks work by a rig with the same owner.
  • Worker safety: the worker treats the coordinator as possibly hostile too: size, time and format limits on every reply, no keys over plain http to another machine, prompts passed to the model in a private file, no secrets in the model's environment, and no admin rights needed.
  • Signed releases: worker code will only count as official when at least two different people from a published list have signed it; a release checker refuses extra or changed files (signers not yet chosen).

7. Verification

7.1 Hidden re-runs (audits)

After a result is accepted, the coordinator may quietly queue the same job again for a different, randomly chosen rig. How often depends on the rig's record: 50% for new rigs (fewer than 5 independently checked results), 100% for rigs with a strike, and a base 25% for established rigs. The auditor is picked with secure randomness among active, eligible rigs; it can't race for audits, and the same owner never audits itself.

7.2 Hidden tests (known answers)

Some jobs are tests whose correct answer the operator already knows, produced by the pinned model on trusted hardware. They look like any other job. A wrong answer is a strike. Tests can be aimed at one rig or at a trust tier (for example, every new rig). They come from a private, owner-only stock; each is used once, and any test whose input has been revealed (including near copies with changed spacing, case or settings) is retired.

7.3 Agreement and tie-breakers

Two answers "agree" if they're equal after collapsing whitespace, a deliberately strict first rule. If an audit disagrees, a third rig (not either side, not their owners) re-runs it as a tie-breaker; the outvoted side gets a strike. Optional settings let only established rigs act as tie-breakers, or let a majority settle only when the rigs on the winning side are established; otherwise the case is held for a person. With only two rigs online, disputes wait in a review queue.

7.4 Following leads

When a rig is caught, a "vouch check" lists every rig that agreed with its answers and every confirmation that rested only on it. One hidden test can then be aimed at each of those rigs with one command.

7.5 What a result is worth

Every accepted result ends in one public bucket: confirmed (checked exactly, re-run agreed, or passed a hidden test), unverified (not picked for a re-run; final), pending (a check is still queued) or held (disputed, outvoted, unresolved or failed a test). A cheater who fakes answers survives an unchecked job with probability 1 − p per job, so faking n jobs goes unnoticed only (1 − p)n of the time, which is 0.75n at the base rate.

8. Keeping checks hidden

Checks only work if a rig can't tell when it's being checked. Several leaks were found and closed during the code audit, each shown on the old code first:

  • The public ledger shows every result as pending for an hour, so a passed hidden test can't be spotted by watching totals right after submitting.
  • Public views don't show result hashes (a re-run that agrees has the same hash as its original) or internal event numbers (a re-check's number followed its original's).
  • Public job counts are taken once per 15-minute window.
  • A new re-check is held out of sight for a random 60–600 seconds and then released at its own second, with its deadline signed from then, so its timing doesn't point at the result it checks.

9. Points and reports

Points are simulated, off-chain bookkeeping. They exist to prove the scoring is reproducible, not to pay anyone, and there is no promise they'll become coins. The current rule (sim-points-v1) counts confirmed and unverified results and nothing else; a candidate penalty rule (sim-points-v2-forfeit: a rig with a strike loses that period's unverified points) is built but off until the owner decides.

At the end of a period the coordinator signs a report with its key. Anyone can verify the signature offline. The operator can also export a redacted ledger copy (no keys, prompts, answers or real names) that lets anyone re-run the report and every consistency check; a later copy can be compared with an earlier one to prove history wasn't edited, deleted or back-dated. Reports and copies go in the public logbook after a 7-day wait, never replaced.

10. Running it safely

The prototype has been through 22 rounds of an internal code audit, each one shown failing on the old code before the fix. Highlights:

  • Hostile input: request size, nesting and number limits; one-line refusals instead of crashes.
  • Guessing and flooding: per-client request limits and a lock-out after 10 wrong keys, tokens or codes, also when they arrive at the same moment; one IPv6 network counts as one client.
  • Files from strangers: ledger copies, reports and rig reports are opened read-only with strict checks.
  • Its own machine: owner-only files for the ledger and keys, a clock that never goes backwards, polite refusals on a full disk, safe backups and restores that can't undo a revocation, a ledger format number, and backups marked so no tool writes into one by mistake.
  • Incidents: an emergency pause and a written incident plan.
  • Supply chain: every dependency pinned to exact, hash-checked files with reviewed licences, a weekly vulnerability check, and CI actions pinned to commits.

An internal audit is not an outside one. An independent review and a bug bounty are still to come.

12. Hardware plan

The first rig is a Ryzen 5 5600X with 32 GB RAM on Ubuntu and two Radeon RX 470s (4 GB and 8 GB). These Polaris-generation cards aren't on AMD's ROCm support list, so the plan is the standard Linux driver (amdgpu) with Mesa's RADV Vulkan driver and llama.cpp's Vulkan backend. Compatibility is unverified until it runs on the machine.

Read-only tools are ready for that day: a hardware inventory (kernel, PCI IDs, drivers, Vulkan devices), a sensor reader (temperature, power, VRAM, clocks), a one-run recorder that proves which card actually did the work, and an evidence check that only counts a test that passed on both cards in different slots. Throughput, stability and how often two honest cards disagree will be published in the logbook.

What these cards can't realistically do: train large models, or heavy GPU rendering in tools that no longer support them. Newer cards would widen that later.

13. The coin (proposal)

A $BNH coin is a proposal, and it comes after the hardware is proven. The working numbers: 60-second blocks with difficulty adjusting every block, a halving every 1,840,860 blocks (3.5 years), a starting reward of 27, a strict cap of about 99,406,440, and a fair launch with no premine (leaning). See Tokenomics for the schedule.

Undecided, and openly so:

  • Chain: a new proof-of-work chain, a fork of an Ethereum-compatible proof-of-work chain, or settling rewards on an existing chain. Ethereum itself can't be mined (proof of stake since 2022). A small mined chain is cheap to attack with rented hash power, so checkpoints and many confirmations would be needed.
  • Algorithm: a memory-hungry design favouring ordinary GPUs and CPUs over ASICs; not yet written.
  • How useful work and mining connect: mining could secure the chain while useful-work points are settled separately, or one could feed the other. No design is chosen.
  • Strict cap or a small permanent reward to keep paying for security.

Before any launch: legal review (securities, money transmission, tax), a public testnet, an independent security review and a separate, explicit decision. Simulated points are not coins and there's no plan to convert them.

14. Later directions

Compute for others

The natural next step is letting outside users bring AI work to the network. That would need a safe way to run other people's jobs on volunteers' machines (today only project-defined task types run), checks that scale to bigger jobs (re-running a long job is expensive), and payments, which need legal review. GPU rental networks already exist; the aim here would be checked, transparent work rather than the lowest price.

A casino, much later

Using the coin in a licensed casino is an idea that depends on a jurisdiction, a licence, age and identity checks, audited provably fair games and responsible-gambling tools. It may never happen. See the casino page.

AgentWiki

An open idea: a site for AI agents and people where hosting is rewarded with storage proofs. Not designed, not built.

15. Risks and limits

  • It may not work on the cards. Old GPUs, new drivers and Vulkan inference may not cooperate. If so, the logbook will say so.
  • Agreement isn't proof. Two or three rigs agreeing means a cheater needed all of them, not that cheating is impossible.
  • Nothing proves which hardware ran a job. A rented cloud GPU, or a CPU, gives the same answers.
  • The coordinator is trusted. Signatures and copies make its honesty checkable, not unnecessary.
  • Legal risk around coins and gambling can end the project faster than any attacker.
  • Coins can lose all their value. Nothing here says what anything will be worth.

16. Roadmap

  1. Inventory the rig and run a smoke test on each RX 470.
  2. Pin the first model and run real AI jobs on each card.
  3. Two real workers, one coordinator: rehearse good and bad submissions on the cards; measure disagreement and tune the tolerance.
  4. Publish the first signed report and ledger copy in the logbook.
  5. Owner decisions: penalty rule, points table, release signers, chain path.
  6. Only then: chain and coin design, testnet, outside audit, legal review.

The live task list is on GitHub.

17. Glossary

  • Coordinator: the service that creates, signs and checks jobs and keeps the ledger.
  • Rig / worker: a volunteer's GPU and the program that runs jobs on it.
  • Audit (re-run): the same job quietly given to another rig to compare answers.
  • Hidden test: a job whose answer is already known, used to catch fakes.
  • Strike: a failed hidden test or being outvoted in a tie-breaker.
  • Ledger copy: a redacted copy of the ledger that anyone can re-check a report against.
  • Simulated points: test bookkeeping; not coins, not money.
